## Context

> The Silk Web Inspector is a Chrome DevTools extension for debugging Silk RPC traffic in WebViews. It lives at `search/frontend/silk/tools/webinspector/`. Design doc: go/silk-client-emulator.

Architecture:

- **app/** — DevTools panel UI. `panel.ts` orchestrates. Already wired up — don't touch.
    
- **common/** — Shared types + `WebPageCommunicationService` (bridge that calls `chrome.devtools.inspectedWindow.eval()` into the page). Already wired up — don't touch.
    
- **injected/** — Content script injected into the inspected page via `eval()`. `silk_web_inspector.ts` is the entry point.
    

The transport layer currently has two spy-only implementations behind a `TransportInstrumenter` abstract class:

- `LegacyPortsTransportInstrumenter` — spies on individual per-service `MessagePort`s
    
- `UnifiedPortsTransportInstrumenter` — spies on the single shared `window.silkPort`
    

Both only observe traffic. They don't modify it.

## What I need

For the unified channel mode, I need a new `TransportInterceptor` that goes beyond spying — it intercepts traffic and can substitute mock responses. It needs to handle two scenarios:

### 1. Simulator mode (no real native backend)

When no real native backend is present, the interceptor creates a fake `MessagePort`. The web page talks to our fake port. We intercept every web→native call, look up mocks, and return mock responses. This enables testing the web page entirely without a native backend — e.g. in a desktop browser.

### 2. Real device mode (real native backend exists)

When running inside a real WebView (AGSA/iGA), a real `window.silkPort` exists. The interceptor sits in the middle. For calls that match a mock, it returns the mock response instead of forwarding to native. For calls that don't match, it forwards normally. All traffic (mocked or real) gets logged to telemetry.

### 3. Manual event triggering

The interceptor exposes a `triggerEvent(serviceName, eventName)` method that injects a synthetic event message (native→web direction) on demand. The panel UI already has a "Send Event" button wired to call this.

## Critical: Feature toggle vs mode detection

### Feature toggle: `ENABLE_SILK_CLIENT_EMULATOR`

The `ENABLE_SILK_CLIENT_EMULATOR` WebDevX preference (`search/xga/xplatform/tools/search_dev_toolkit/shared/preferences/preferences.ts`) is the on/off switch for the entire client emulator feature. When it's off, use the plain `UnifiedPortsTransportInstrumenter` (spy-only). When it's on, use the new `TransportInterceptor` (spy + mock). This preference is already defined but not yet consumed — wire it up in the factory.

### Mode detection: simulator vs real device

You CANNOT check whether `window.silkPort` exists to determine the mode. Checking for the port introduces a timing issue — the interceptor must install itself instantly at injection time, before any page-load messages fire. If you wait to check for the port, you'll miss the first messages.

Instead, use a synchronous signal available at injection time. The best option is `navigator.userAgent`: in AGSA's WebView, the UA string contains identifiable markers (e.g. `GSA/`, or Android WebView markers like `wv`). A desktop Chrome UA won't have these. This is a single synchronous string match — zero latency.

The interceptor should decide its mode immediately, synchronously at construction time based on the UA. No async reads, no waiting for ports.

## Design guidance

Think of this as a message middleware. Every web→native message passes through one function that decides: mock it or forward it. The two modes (simulator vs real device) only differ in what "forward" means — in simulator mode there's nowhere to forward, in real device mode it goes to the real port. Keep the interception logic in one place, not duplicated across modes.

The whole interceptor should be under 200 lines. If it's growing past that, step back and simplify.
