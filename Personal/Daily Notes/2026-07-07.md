# Silk Client Emulator [KSB's met: K1, K3, K4, K5, K7, K8, K10, K12, S2, S3, S5, S8, S9, S13, S14, S15, S17, B1, B4, B5, B6, B7, B8, B9]

**For my third project, I was tasked with creating a usable Client emulator for Silk, in order to help developers using Silk to test their web-to-client integrations.**

### **Situation**

Developing and testing features that use Silk can be cumbersome. Currently, developers often need to build and deploy the entire AGSA (or iGA) application onto a physical device or an emulator to test the interaction between their web code and the native Silk implementations. This process can be slow and inconsistent, hindering the quick development cycle needed for features that need to ship fast, such as AI mode.

There's no easy way to isolate and test the Silk integrations in a lightweight environment. Developers lack a tool to quickly mock or simulate the behavior of the native Silk services that their web features depend on. This absence makes debugging and verifying the web-to-native communication layer inefficient. To address this, the idea for a Silk Client Emulator was proposed. Such a tool would allow developers to test their Silk-dependent web features in a more isolated and controlled manner, without the overhead of the full AGSA application.

This necessity was highly visible within the organisation. We received direct feedback from the AIM team highlighting this exact gap: _"We go in blind when either side is missing or just submitted but not in [production]. Being able to verify changes - or verify bugs - directly in a desktop browser will be really big for velocity."_ Previously, an attempt had been made via a proof-of-concept by a former team member (Chloe Beardsley), but it was never fully implemented and only supported sending method responses, not events. Furthermore, recent AIM-related outages (e.g., omg/93617 and omg/95633) underscored the need for isolated testing.

I was already in the middle of working on the Silk Web Inspector and the 6~ features we had outlined for it as mentioned before, so this came as a bit of a curveball. It was classified as a P0, which is the highest priority (my other stuff was P1 or P2) - I was kind of in a “drop-everything-and-focus-on-this” situation with this.

### **Action**

**Software Design & Architecture** I began by creating simple software designs to communicate the architecture to my stakeholders. Since the existing Silk Web Inspector already intercepted messages between the web and the client by replacing the `silkPort`, I reasoned that extending this tool was the best design approach. I designed an intermediary gatekeeper: if a developer enabled client emulation, the tool would intercept specific web-to-native calls, match them against a stored map of mocked responses, and return the mock instead of forwarding the call to the real client.

To implement this, I led the architectural restructuring of the extension. Moving away from a flat file structure, I migrated the codebase to a modular design (`injected`, `app`, `common`). I created a dedicated class, `MockHandler` (initially named `ClientEmulator` in CL 915923499), to manage interception logic. I modified `unified_ports_transport_instrumentor.ts` so that it would query the `MockHandler` for existing mocks before passing messages across the port channel.

**Data Storage & User Interface Integration** To link this code to data sets, I designed a schema to store the mocks using non-relational, key-value principles. I defined a TypeScript interface:

TypeScript

```
export declare interface silkMocks {
  [key: string]: { // Keyed by service name
    methods: Method[];
    events: Event[];
  };
}
```

I stored this object using the `chrome.storage.local` API. This ensured that developers wouldn't lose their inputted mocks between browser sessions. To remain compliant with organisational policies and security procedures regarding data treatment, I consulted with the WebDevX team (specifically ahornacek@) to ensure it was safe to inherit these storage permissions via their `manifest.json` without introducing new external dependencies.

For the User Interface, I extended the tool's panel. I developed an effective UI component that allowed users to input the Service Name, Method/Event Name, Message Type, and the Base64 encoded protobuf data. I utilised HTML datalists to make service field inputs easier (CL 921982733). I also designed a `BaseTabView` class pattern so that future features (like Web Emulation) could be easily added to a scalable tab-based navigation layout.

**Solving Complex Problems with Tenacity** During development, I faced several major technical hurdles that required significant initiative and resourcefulness. First, I discovered an issue where Silk JS modules were not being served for the emulator. I spent a full day debugging this—checking user agents, mimicking `X-Client-Data` headers, and running GWS locally. I finally discovered that the `X-Silk-Capabilities` header I was manually supplying was an invalid base64 string, preventing the `silkPort` from initialising entirely. Before I could build a long-term dynamic header generator, I documented a secure workaround for developers using the internal Zwieback-Forge extension, utilizing an intern permission key to spoof the header.

While working on the message payload decoding, my curiosity regarding the business context led me to investigate how AGSA encodes Silk data into base64. I discovered a massive flaw specifically on Android clients: **Silk was sending roughly 11.35TB of redundant data a year** due to base64 wrapping. I filed a bug (`b/521829806`) and wrote a proposal (`go/silk-b64-no-wrap`) to fix this using URL-safe base64 encoding, which will result in a global latency decrease for Silk on AGSA clients.
